# PostgreSQL migrations

These SQL migrations are the hosted API schema source. Apply them with the explicit `pos-api migrate` command, which embeds the ordered migration files and uses SQLx's migration tracking/checksum mechanism. It reads only `POS_API_MIGRATION_DATABASE_URL`; the API server does not apply migrations at startup. Use a dedicated migration credential and never reuse it as the runtime API database credential.

From the repository root, run `./tools/verify-api-postgres-migrations.ps1` to start a disposable PostgreSQL 16 container, apply the migrations twice, verify the SQLx migration ledger, exact provider identity matching, restricted runtime grants, tenant RLS, cross-tenant constraints, and hosted API requests through the restricted login, then remove the container. It exercises concurrent station capacity allocation, signed activation proof and challenge replay denial, owner-only activation revocation, challenge cancellation, active lease termination, slot release/reactivation, and cashier lease acquisition/heartbeat/release. It requires Docker Desktop and does not use a persistent volume. Docker CLI calls have bounded timeouts so a stalled engine does not leave the verifier waiting forever; if the engine cannot respond, cleanup may need to be retried after Docker recovers.

`0001_tenant_identity_foundation.sql` creates vendor-neutral tenant, external person identity, membership, branch, station, scoped role grant, and audit records. `0003_station_entitlements_and_activations.sql` adds operator-provisioned tenant entitlements and owner-authorized station activation records; it enforces numeric active station capacity independently of staff count. `0004_station_actor_leases.sql` adds short-lived hosted cashier leases, with one-time opaque tokens stored as SHA-256 hashes, heartbeat, explicit release, retained lease history and a separate station lock. `0005_station_activation_challenges.sql` adds five-minute, single-use owner challenges; activation verifies an Ed25519 signature over the tenant, branch, station, challenge, nonce and public key before binding the key. `0006_station_activation_revocation.sql` records the owner and required reason for revocation, cancels outstanding challenges, ends any live cashier lease and removes its lock atomically. `0007_device_bound_cashier_leases.sql` binds each lease to its activation and requires a fresh cashier-specific one-time challenge signed by the active station key before lease creation. `0008_hosted_catalog_inventory.sql` adds tenant-wide product identities, branch-specific price/tax/stock settings, append-only stock movements, branch currency, strict tenant RLS, and audit insertion. `0009_hosted_stock_adjustments.sql` adds resulting stock snapshots and the manager-scoped balance update policy. A stock adjustment updates the branch balance, appends an idempotent movement and audit event in one transaction; its `Idempotency-Key` makes an exact retry replay the original result. `0010_cross_branch_stock_availability.sql` adds a narrowly scoped RLS policy for authorized register availability lookups. A cashier can search an active branch product across active branches and see branch name/code, price, currency, and stock quantity; costs and unrelated tenant rows stay hidden. `0011_branch_product_status.sql` allows managers to archive/restore a product at one branch while retaining stock history and other branch entries. `0012_tenant_product_identity_edit.sql` adds revision-checked edits to tenant-wide SKU, barcode, name, description and category; these require tenant-scoped permission, update every branch's shared identity, preserve branch stock, and record an audit event. The API also supports branch-specific price, tax and stock-alert updates with revision checking, plus product creation and idempotent stock adjustment. Product transfers/receiving, purchase receiving, safe/petty-cash transfer accounting and automated processor capture remain unimplemented. Migrations use `(issuer, subject)` rather than email as the provider identity key and composite foreign keys to reject cross-tenant relationships. DDL targets PostgreSQL 14 or newer. SQLx wraps each migration in a transaction; do not add explicit `BEGIN` or `COMMIT` statements to migration files.

Before exposing additional business workflow routes (sales, inventory mutations, finance or staff):

1. Run `pos-api migrate` once per deployment using the dedicated migration credential; the migration command uses one connection and SQLx's migration lock/tracking table.
2. Create separate owner/migration and runtime database credentials. The runtime role must not own tenant tables, be superuser, or have `BYPASSRLS`.
3. Extend `FORCE ROW LEVEL SECURITY` and transaction-local identity/tenant context policies to every new tenant-owned table. Set context only after the Rust API resolves it from a verified identity and active membership; never from an untrusted request field.
4. Add API authorization checks for active identity, active membership, active tenant, resource ownership, scope grants and action permission. The current membership bootstrap route only lists granted context; it does not authorize business operations. RLS is defense in depth.
5. Add integration tests against the same PostgreSQL major version and restricted runtime role used in deployment. Prove cross-tenant reads/writes, stale memberships, inactive branches/stations, role downgrade, activation capacity/concurrency and transaction-pool context reset are denied.
6. Test migration from an empty database and from each released schema version, including restore from backup.

Runtime API routes need a credential separate from the migrator. Migrations enable and force RLS for identity, tenant, membership, role-grant, branch, station, catalog, inventory and audit access. The API sets `pos.verified_issuer` and `pos.verified_subject` only after provider introspection; after matching the internal identity it sets the internal identity, tenant, membership, branch and station context in each request transaction. The cross-branch availability route additionally sets `pos.inventory_availability` only after checking the assigned station's server-side permission. These values are transaction-local and never taken from request parameters. A deployment administrator substitutes the actual runtime role name and grants only the columns required by the current routes and policy expressions:

`GET /v1/auth/identity` maps the verified `(issuer, subject)` pair to an active internal identity. `GET /v1/me/tenants` then returns only that identity's active tenant memberships, scoped roles, and branches/stations allowed by those grants. It does not accept a tenant or identity ID from the client. Do not grant broad table access as a shortcut. Keep TLS certificate verification enabled for hosted database URLs.

Migration 0011 (0011_branch_product_status.sql) allows managers to archive or restore a product's branch catalog entry under branch-scoped RLS. The API preserves stock and movement history, leaves other branch entries active, increments the revision, and records an audit event in the same transaction. The runtime role receives update permission only for the status column in addition to the existing stock-adjustment columns.

Branch managers can also change branch price, tax rate and stock alert levels using the product's expected revision. This avoids lost updates when two managers edit the same product; stock quantity remains writable only through stock movement workflows. The runtime grant lists the specific editable columns; server authorization and RLS are still required.

Migration 0012 (`0012_tenant_product_identity_edit.sql`) adds a revision to shared tenant product identity and a tenant-scoped management update policy. `PATCH /v1/tenants/{tenant_id}/products/{product_id}` changes SKU, barcode, name, description and category across all branches without touching branch stock or pricing. It checks `expectedRevision`, rejects duplicate identifiers, and commits an audit event with the identity update. Runtime column grants are listed below and must be combined with the verified tenant-level `products:write` authorization.

Branch catalog management can also list active tenant product identities not yet attached to a selected branch and attach one by exact product ID. The manager provides branch-specific price, tax, opening stock and stock alert values; positive opening quantity creates an opening stock movement, and the event is audited in the same transaction. This prevents new duplicate identities when adding the same item at another branch. It does not merge product identities that were already created separately, and it never infers a match from similar names.

Migration 0013 (`0013_branch_payment_options.sql`) adds branch-scoped tender options with role-filtered reads, owner/admin/manager writes, revision-checked updates, retained disabled rows and audit events. Provider and country fields are reference labels only. Every option is explicitly `recording_mode = 'manual'`; the table stores no merchant secret and does not indicate processor approval. Cashiers can read options at assigned stations but cannot create or edit them. The restricted runtime role has only required column-level select/insert/update grants.

Migration 0014 (`0014_station_financial_proof_challenges.sql`) adds short-lived challenges bound to an active station activation, cashier lease, financial-operation idempotency key and client payload hash. `POST .../checkout-challenge` requires the current station lease token and a cashier-scoped `sales:checkout` grant; it returns the exact canonical message for the device key to sign. Allowlisted targets include sale commit and drawer open, movement and close operations; movement/close challenges bind the shift UUID into the signed path.

Migration 0015 (`0015_hosted_sales.sql`) adds forced-RLS sale, immutable line and manual-tender snapshot tables plus cashier sale policies. `POST .../sales` recomputes the exact request hash, verifies and consumes a fresh challenge, revalidates the active lease/activation and cashier role, locks and decrements stock, and records receipt, lines, tenders, stock movement and audit in one transaction. Non-cash tenders must be configured manual options; automatic provider approval/capture is not implied.

Migration 0016 (`0016_hosted_drawer_shifts.sql`) adds one active hosted drawer shift per station, idempotent drawer movement rows, signed open/movement/close challenges, and an immutable Z report snapshot. Cash tenders require the live station shift and are included in the expected-cash calculation. `GET .../drawer-shift` and `GET .../x-report` return the live X snapshot without closing. All financial writes use a station advisory lock, current cashier lease and activation, body-bound one-use Ed25519 proof, RLS and restricted column grants. Expected cash is opening float + cash tenders + paid-in - paid-out - cash drops. Apply the least-column grants in `docker/grant-runtime.sql` to the restricted runtime role; schema migrations deliberately do not assume that runtime role exists.

Migration 0017 (`0017_stock_transfers.sql`) establishes durable branch-to-branch transfer, line and append-only event records; migration 0063 (`0063_incremental_transfer_receipts.sql`) adds batch receipt and explicit short-shipment resolution states. Transfers are tenant-scoped and RLS-visible only to authorized staff at the source or destination branch. The API implements manager accept/reject, source dispatch, incremental destination receipts, and discrepancy resolution from either partial-receipt or discrepancy state. Dispatch debits source stock; each receipt credits only the newly delivered physical units. Cumulative received quantity cannot exceed dispatched quantity. Revision checks, per-action idempotency, stock movements, transition events and audit records share one transaction. A receipt without a final discrepancy note stays open for later deliveries. A short shipment can be explicitly closed with a reason; that action records the disposition and does not change stock. On 6 November 2026, all 63 PostgreSQL migrations applied twice and the restricted HTTP integration passed two one-unit receipt batches, replay of both idempotency keys, closure of the remaining short shipment, and final balances of destination 12/source 0 with three transfer movements total.

Migration 0018 (`0018_hosted_customers.sql`) adds tenant-wide customers with forced RLS, branch/station-grant visibility, normalized contact data, creation audit events and membership-scoped idempotency records. A restrictive hosted-sale insert policy permits a customer association only when the checkout actor can see that active customer from the sale's branch/station context. The restricted runtime can read only required customer fields and cannot delete customer records. The API supports bounded case-insensitive name/phone/email search and paging. Cashiers can list/create walk-in customers and link a customer during signed checkout.

Migration 0019 (`0019_hosted_customer_management.sql`) adds optimistic revisions and manager-only update/archive/restore policies. Owners/admins/managers can edit details, view archived entries, archive and restore records through `customers:manage`; cashier access is denied by both the API permission check and RLS policy. Customer changes are audited in the same transaction. The restricted PostgreSQL verifier covers search/page bounds, manager update/archive/restore, stale revisions, cashier denial, exact retries, cross-tenant denial and customer-linked checkout.

Migration 0020 (`0020_hosted_suppliers.sql`) adds a tenant-wide supplier directory scoped through the active branch grant. Forced RLS protects reads and writes; runtime column grants are least-privilege and supplier records cannot be deleted. Managers with `suppliers:read` can search and page active entries; `suppliers:write` permits idempotent create, revision-checked edits, and archive/restore. Mutations are audited. Migration 0029 adds supplier image storage; purchase orders and invoice/settlement workflows are described in their later migrations.

Migration 0021 (`0021_hosted_purchasing.sql`) adds branch-scoped purchase-order drafts, immutable product/SKU snapshots, idempotent partial/final receipt records, and forced RLS across all four purchasing tables. `purchases:write` permits managers to create/edit/place/cancel orders; `purchases:invoice` permits receiving deliveries. Receiving updates branch stock, appends one stock movement per received order line, snapshots the actual unit cost on the branch item, updates order status/revision, and writes audit records in one transaction. Replaying the same receipt key and payload does not post stock twice. The actual unit cost policy is last received unit cost, matching the local desktop implementation; it is not a weighted average. Marking an order placed is a record-only action and does not message the supplier.\n\nMigration 0022 (`0022_hosted_supplier_bills.sql`) adds immutable branch-scoped invoice records and allocations against supplier-matched delivery receipts. The API serializes allocations with transaction-scoped advisory locks keyed by each receipt, enforces invoice totals equal allocations, prevents duplicate invoice references per supplier and branch, supports exact idempotent retry, and writes an audit event. Forced RLS limits visibility and writes to owner/admin/manager branch grants; the runtime role has select/insert columns only. Invoice source journals are added in migration 0023; payment, drawer and cash-location effects are described there.


Migration 0023 (0023_hosted_supplier_settlement.sql) adds immutable manual supplier-payment records, bill allocations, and source journal headers/lines. suppliers:settle is owner/admin-only by default; managers can view bill/payment balances but cannot record settlement. Invoice matching posts Dr GRNI / Cr Accounts Payable, and a payment posts Dr Accounts Payable / Cr the method's built-in cash or tender-clearing account. Deferred database constraints reject unbalanced journals; payment allocation locks prevent concurrent over-settlement. All four new tables force RLS and have least-column runtime grants without update/delete access. The API records a tenant-reported external payment and does not initiate or verify it; the journal does not update hosted drawer or cash-location balances, and wider financial statements remain incomplete until receipt-side and sales/expense posting coverage is complete.

Migration 0024 (`0024_supplier_payment_drawer_link.sql`) adds a nullable supplier-payment source link to hosted drawer movements, restricted to `paid_out` movements and unique per source payment. Cash supplier payments use the station-scoped supplier-payment endpoint, require supplier settlement permission and a signed active cashier lease, and insert the payment, allocations, balanced journal, audit event, and linked drawer outflow in one transaction. Exact retries require a fresh signed challenge and return the same payment without duplicating the movement. The runtime receives select/insert access to the source-link column only; it cannot update it. Cash payments from non-drawer locations remain unsupported by the hosted client until the hosted cash-location ledger is implemented.

Migration 0025 (`0025_supplier_payment_financial_proof.sql`) adds `supplier.payment` to the existing station financial-proof operation allowlist. The challenge target is the station supplier-payment path and binds the open drawer shift UUID as its resource.

Migration 0026 (`0026_hosted_payment_integration_requests.sql`) adds a branch-scoped, append-only intake table for tenant requests about unsupported banks, terminals and payment providers. Owner/admin/manager users with `payments:write` can create idempotent requests and view their latest status; forced RLS, least-column grants and an audit event protect submissions. Credential and payment-account markers are rejected in free text. This records a support request only: the separate operator auth audience, inbox/Kanban, progress updates, provider connector and payment capture are not part of this migration.

Migration 0029 (`0029_hosted_entity_images.sql`) adds tenant-owned PNG, JPEG, and WebP image storage for products, customers, and suppliers. The API bounds uploads at 2 MiB, verifies MIME signatures, keeps bytes out of normal record payloads, applies branch-scope permissions and forced RLS, and serves bytes only to authenticated authorized members. Uploads replace the current image; deletes are audited. The database implementation is a small-asset MVP; production scale may move the same API contract to private object storage with tenant-scoped signed access.

Migration 0030 (`0030_hosted_sale_customer_links.sql`) adds an append-only, one-per-sale customer association for completed sales that were checked out as walk-ins. A station cashier may link only their own completed sale; owner/admin/manager access follows branch grants. Exact retries are safe, different-customer reassignment conflicts, and totals, tenders and stock are unchanged. Migration 0031 (`0031_hosted_receipt_snapshots.sql`) stores customer display-name snapshots and adjusts association reads to inherit scope from the parent sale's RLS policy. Station and branch receipt-detail endpoints return immutable line and tender snapshots for view/reprint. The station sales-history endpoint searches receipt, customer, item/SKU/barcode, and tender snapshots while forced RLS keeps cashier results scoped to their own sales at the assigned station. Runtime reads and inserts are granted by column only; the restricted verifier covers repeated migrations, snapshot grants, station and branch receipt access, customer-name stability after later profile edits, and station history search bounds.

Migration 0032 (`0032_hosted_refunds.sql`) adds append-only hosted sale refund headers, per-line quantities and restock dispositions, manually recorded refund tenders, `voided` sale state, and a source-linked cash drawer outflow. The station API requires `sales:refund`, a current cashier lease/activation, a fresh body-bound station signature and idempotency key; it serializes refunds per sale and uses cumulative per-line subtotal/tax allocation so repeated partial returns sum exactly to the recorded line total. Cash refunds require an open drawer with sufficient expected cash. Non-cash methods require a provider reference but do not contact or verify the provider. A void is limited to the first complete return of every sale line. Restricted PostgreSQL HTTP coverage exercises a cash void/retry and staged taxable partial returns with cumulative rounding, required non-cash references, status snapshots and explicit stock-restock behavior. Financial statement coverage remains incomplete until hosted sales and expenses are journaled.

Migration 0033 (`0033_hosted_expenses.sql`) adds immutable branch expense sources with a manager/owner/admin-only read/write surface, a restricted runtime role, idempotent create requests, audit events and balanced journals. Expense categories post to operating-expense accounts 5000–5900; non-cash methods post against matching payment-clearing accounts. Payment is reported by the tenant and is not initiated or provider-verified. Expense records are append-only; reimbursement and cost-center correction policies remain separate workflows.

Migration 0034 (`0034_hosted_customer_merges.sql`) adds explicit owner/admin/manager customer deduplication. The active source becomes a merged alias that points at an active target; merge records are append-only, exact request retries are safe, and changed retries conflict. The RLS insert policy matches each event to both customer rows and their revisions, and a deferred constraint trigger rejects a merged profile without its matching event. A survivor cannot be archived while aliases point to it. The merge never edits past sale customer associations or receipt snapshots, and it does not transfer customer credit or loyalty balances. Forced RLS and least-column grants keep cashier management access denied and prevent runtime changes/deletion of merge history.

Migration 0035 (`0035_hosted_drawer_expenses.sql`) adds signed cashier cash expenses. The station endpoint requires the dedicated `expenses:cash:write` permission, an active station lease, a one-use challenge bound to `expense.payment` and the exact drawer shift, and a matching open shift. The expense, balanced category-to-cash journal, audit event and source-linked drawer `paid_out` are atomic. Forced RLS and narrow runtime grants limit cash expense writes and journal entries to the active cashier station; exact retries do not create another movement.

Migration 0036 (`0036_hosted_cash_locations.sql`) introduces branch/currency-scoped physical cash locations, immutable opening and transfer events, immutable transfer headers, derived balances, forced RLS and append-only least-column grants. The branch API supports safe/petty-cash/other locations, one-time counted openings, balanced two-leg transfers, retry protection and event history. Register locations are reserved for the station-integrated workflow and cannot be opened or transferred through these manager branch routes. These movements do not post another GL entry; a separate explicit cutover workflow reconciles measured branch cash to account 1000.

Migration 0037 (`0037_hosted_cash_location_expenses.sql`) links manager-recorded cash expenses to an active initialized safe or petty-cash location. Expense source, balanced operating-expense/cash journal, audit event and signed location outflow are atomic; a deferred constraint requires one matching event for each location-funded cash expense, and an advisory lock prevents concurrent overspending. Exact retries do not duplicate outflows. Register cash continues through the signed cashier drawer route. Safe-location expense movements do not create another GL posting. Supplier settlements and manager safe/petty-cash expense reimbursements are now implemented in migrations 0038–0039. Migrations 0041–0048 link register sales/refunds, source cash outflows and cash drops, and add explicit cash cutover; manual paid-in/paid-out movements remain unresolved review items until a supported classification workflow is implemented.

Migration 0048 (`0048_hosted_cash_reconciliation.sql`) adds an immutable branch cash cutover record and owner/admin-only reconciliation endpoint. It requires every active cash location to have an opening count and every drawer shift to be closed, then compares the measured physical-cash subledger total with posted account 1000. A nonzero difference posts a balanced cash/opening-equity journal (accounts 1000 and 3000) in the same serializable transaction. Idempotent retries return the saved record; changed retries conflict. The live status reports uninitialized locations, open shifts, variance and manual register movements that are not classified as sales, refunds, expenses, supplier payments or cash drops. Manual movement amounts are never guessed into revenue or expense.

Migration 0038 (`0038_hosted_cash_location_supplier_payments.sql`) extends branch-level supplier settlement to cash paid from an initialized safe or petty-cash location. The immutable payment, invoice allocations, balanced AP/cash journal, audit event and source-linked negative cash-location event commit atomically; exact retries do not duplicate the outflow. A deferred source-event constraint and unique link prevent orphan or duplicate events, while advisory location locking protects against overdraw races. Cash paid from a till remains on the signed station drawer route. Supplier cash-location history is visible in the branch cash ledger; provider transfers remain tenant-reported and are not initiated or verified by the app.

Migration 0039 (`0039_hosted_expense_reimbursements.sql`) adds manager-recorded partial or full expense returns. Each return is idempotent, capped at the original expense's unreimbursed balance and posts a balanced reversal journal. Cash returns must name an active initialized safe or petty-cash location and create one immutable positive cash event in the same transaction. Forced RLS, least-column grants, duplicate-reference protection and a deferred source-event constraint keep the source, cash event, audit row and journal linked. Register drawer receipt remains a separate signed station workflow.

Migration 0049 (`0049_hosted_branch_profile.sql`) adds address, phone, email and revision-checked weekly opening hours to each branch. Owner/admin `settings:write` permission is required for changes; the database update policy and least-column grant restrict runtime updates to assigned active branches. Changes append a branch audit event. Opening hours are expressed in branch-local time with up to four non-overlapping same-day periods per weekday.

Migration 0050 (`0050_inventory_allocations.sql`) adds a quantity-only commitment ledger for accepted outbound transfers and future customer pickup holds. Availability reports on-hand, pickup-held, outbound-committed, available-to-promise and shortfall without customer details. Existing accepted transfers are backfilled without inventing stock, so legacy overcommit remains visible as a shortfall. Source-branch transfer acceptance creates the commitment; dispatch releases it atomically with stock movement.
