# Pickup reservations: shared commitment ledger

## Caller flow

1. A cashier at a station requests a fresh availability view for a canonical product. Each branch shows physical on-hand, customer holds, accepted outbound transfers, available-to-promise (ATP), any shortfall, and server observation time. A snapshot is not a guarantee.
2. The cashier selects the branch the customer will visit, quantity, customer name and phone or an existing customer, and a bounded expiry. `createPickup` atomically checks current ATP and returns a reservation reference and expiry. It reserves immediately; it does not create a sale or move stock. If the client is offline or the request's outcome is unknown, it retries the same idempotency key, never makes a second hold.
3. The pickup branch's cashier or authorized manager sees its incoming queue, can mark a hold ready or cancel with a reason, and identifies the customer using a reservation reference plus the business's normal identity process. The requesting cashier can see and cancel their own request. The UI shows a clear expiration and that payment occurs at pickup.
4. At the pickup branch a cashier selects the hold in the register and commits a sale containing the reserved quantity. Checkout atomically consumes the hold and posts the sale and stock movement. It never releases the hold before the sale commits. An expired or stale hold cannot be consumed. The transaction rolls back the hold consumption on checkout failure.

```ts
type Availability = { branchId: UUID; onHand: bigint; heldForPickup: bigint;
  committedToTransfers: bigint; availableToPromise: bigint; commitmentShortfall: bigint;
  observedAt: Instant; /* branch identity, price, contact and hours as today */ };
type Pickup = { id: UUID; reference: string; requestBranchId: UUID; pickupBranchId: UUID;
  productId: UUID; quantity: bigint; customerId: UUID | null; contactName: string;
  contactPhone: string | null; status: 'reserved' | 'ready' | 'collected' | 'cancelled' | 'expired';
  expiresAt: Instant; revision: bigint; createdAt: Instant; saleId: UUID | null };
type CreatePickup = { pickupBranchId: UUID; productId: UUID; quantity: bigint;
  customerId: UUID | null; contactName: string; contactPhone: string | null; holdMinutes: number };
type ChangePickup = { action: 'ready' | 'cancel'; expectedRevision: bigint; reason?: string };
// The API accepts Idempotency-Key for create and transition.
POST /tenants/{t}/branches/{requestBranch}/stations/{station}/pickup-reservations  CreatePickup -> Pickup
GET  /tenants/{t}/branches/{branch}/stations/{station}/pickup-reservations -> Pickup[]
GET  /tenants/{t}/branches/{branch}/pickup-reservations -> Pickup[]
POST /tenants/{t}/branches/{branch}/pickup-reservations/{id}/events  ChangePickup -> Pickup
// Extend the existing signed station sale request with pickupReservationId and expected revision.
```

Use decimal integer representations compatible with existing API constraints; JavaScript clients must reject values outside `Number.isSafeInteger`. Keep the first implementation to a single canonical product per hold and exact full-quantity checkout. Multiple holds can be consumed in one sale after acquiring their locks in deterministic order. Partial collection requires a later explicit split/remaining-quantity model, rather than silently releasing the remainder.

## Existing code and why coordination is required

`branch_catalog_items` is canonical per `(tenant, branch, product)`. `catalog::product_branch_availability` uses a transaction-local availability GUC for cross-branch RLS. `stock_transfers::transition` currently accepts at the destination and writes accepted lines without checking source availability; dispatch later debits stock. `sales::commit` locks the product row but checks only physical `stock_quantity`, and `catalog::adjust_branch_stock` can reduce on-hand based only on zero. A new reservation table alone therefore cannot protect a hold: an ordinary sale, adjustment, or accepted transfer can consume it. Close these paths in the same release. The existing transfer state machine must change so the source branch accepts/rejects, with the UI, contract and tests updated; accepting a request is an actual source inventory commitment. Existing accepted transfers need a migration audit for shortfalls before they can be treated as guaranteed commitments.

## Data model and access

Add `pickup_reservations` with tenant-composite foreign keys to origin branch/station, pickup branch, canonical product, optional tenant customer, creator membership and optional consuming sale. Preserve contact snapshot and product name/SKU snapshots for fulfillment; avoid contact values in audit metadata. Store bounded positive quantity, database-created expiry, status, revision, idempotency key and normalized request hash. A random unguessable reference is a lookup convenience, never an authorization credential. Make the active states `reserved` and `ready`; a non-expired row in either state counts as a commitment. A collected row references exactly one committed same-tenant, same-pickup-branch sale and cannot become active again. Enforce state/timestamp consistency and immutable identity, quantity and initial expiry with constraints/triggers, composite FKs, and column-limited update grants.

Add append-only `pickup_reservation_events` with actor or explicitly typed system-expiry actor, branch, action, old/new revision, reason, idempotency key/hash and server timestamp. Unique `(tenant, reservation, actor, idempotency_key)` plus unique revision prevents duplicates. Apply forced RLS to both tables. Runtime SELECT on contact columns is limited to branch fulfillment staff and the requesting member; the availability view cannot use this policy to expose contact details.

Use a separate minimal `inventory_commitments` projection keyed by tenant/branch/product plus `(kind, source_id)` and carrying only quantity, expiry and active/released state. It covers pickup holds and accepted transfer lines. Its forced-RLS availability read grants only the current verified tenant membership, authorized origin branch and station, and only during the transaction-local availability scope. It contains no customer/contact details. All writes are coupled in the parent transition transaction; use composite FKs, unique source rows, restricted column grants and deferred constraints/triggers so a reservation or accepted transfer cannot commit with a missing/mismatched commitment. Do not grant runtime direct delete. Alternatively an audited, narrowly defined database aggregate function may replace this table if its owner, `search_path`, privileges and caller authorization are independently reviewed; avoid granting unrestricted cross-branch access to reservation contact data.

Permission baselines: owner/admin/manager can create holds at their permitted station, see/manage holds at their branch, and authorize source transfers; a cashier can create at an assigned station, see/cancel their own outbound requests and see/fulfill their pickup branch's queue at their assigned station. Cashier checkout still requires the existing `sales:checkout` and signed station proof. Introduce explicit `inventory:pickup:create`, `inventory:pickup:read`, `inventory:pickup:fulfill` permissions and enforce both HTTP scope and RLS using active tenant, identity, membership, branch/station grants. Managers without station access use branch-scoped queue routes. The event action checks whether the actor is at the pickup branch or owns the origin request; a request from another branch cannot read others' contacts. Never trust branch, identity, actor, expiry timestamp, or price supplied in the body.

## Transactions and concurrency

Define one deterministic transaction-scoped advisory lock key per `(tenant, branch, product)`, acquired in sorted `(branch, product)` order for every operation changing available quantity or commitments. Using an advisory lock avoids requiring the requesting cashier to acquire `FOR UPDATE` on another branch's stock row, which its RLS update policy correctly forbids. Keep the existing product row lock for the actual branch write, but always acquire the common advisory lock **before** it. Apply this protocol to hold creation/cancel/checkout, transfer accept/reject/cancel/dispatch, ordinary sales, negative stock adjustments and every other decrement path. Incoming stock updates also take it for a consistent ordering. Multi-product operations sort keys. Lock timeout/deadlock errors return retryable errors; clients keep the same idempotency key.

After locking, read on-hand and the active commitment ledger using a fresh database clock (`clock_timestamp()` evaluated after any lock wait). Derive `ATP = max(0, onHand - activePickupHolds - acceptedOutboundTransfers - configuredSafetyStock)` and report `shortfall = max(0, active commitments + safety stock - onHand)` separately. A create or transfer acceptance fails with a conflict and refreshed ATP when its quantity exceeds ATP. Existing accepted transfer lines count until dispatch; dispatch atomically reduces on-hand by dispatched quantity and releases the whole accepted commitment, so an undispatched remainder is freed rather than counted twice. Cancellation/expiration releases a hold; checkout consumes it while excluding only that same hold from the available check and then decrements physical stock. Other active commitments remain protected.

Negative stock adjustment that would violate live commitments fails with a conflict identifying a commitment shortfall, unless a separately permissioned and audited exception workflow explicitly resolves affected commitments first. Never silently cancel holds. For existing inconsistent accepted transfers, expose a shortfall for management resolution and block new commitments, rather than invent stock or silently demote them.

Idempotency: before allocation, acquire a lock on the tenant/member/key and query the saved request hash. An exact replay returns the original reservation and current effective status; same key with changed body conflicts. Each transition first checks event replay, then locks the reservation row and verifies status, branch, revision and expiry. Insert the reservation, commitment, event and audit in one transaction. Return conflict on stale revision, insufficient ATP, expired hold, wrong branch/state, or changed replay. Validate distinct IDs, positive safe quantities, bounded name/phone and hold duration at the HTTP boundary.

Expiry must work without a worker: availability and checkout treat `expires_at <= database_clock` as expired immediately, so stock is reusable. A durable worker discovers due IDs without taking reservation row locks, then for each candidate takes the common product lock before a reservation row lock, rechecks expiry, writes one system expiry event and moves the snapshot to `expired`; repeated jobs are idempotent. This preserves the same lock order as checkout and avoids a worker-versus-sale deadlock. Until swept, responses derive effective `expired` from timestamp and never display `reserved`. The worker uses a separate least-privilege role; test stopped-worker behavior and restart. A committed sale at the exact expiry boundary is decided once under the common lock and database time, not the client's clock.

## UI and verification

The cashier availability row includes a “Hold for pickup” form with quantity, contact and expiry; confirm only after the API returns the reference. A refreshed/stale/offline indication must distinguish a previous snapshot from a live request and disable creation offline. The pickup queue offers search, expiry, ready/cancel actions, conflict refresh and a “Use in sale” action at the assigned station. Build responsive desktop/tablet and mobile views; avoid exposing another cashier's origin requests or customer contact in broad availability results.

Restricted PostgreSQL plus HTTP tests must cover tenant and station isolation, destination pickup staff access, origin-owner privacy, active membership checks, exact retry and changed body, stale revision, cross-branch product mapping, action permissions, and audit/commitment one-to-one constraints. Race independent connections for hold vs hold, hold vs sale, hold vs negative adjustment, hold vs transfer acceptance, and sale vs dispatch; assert no oversubscription and no deadlocks. Verify expiry without worker, worker replay, time-boundary behavior, rollback after checkout failure, sale/hold atomic link, a partial transfer dispatch's released remainder, existing overcommitted transfers, and absence of customer data from availability. Verify an authenticated cashier and pickup-branch workflow in the web client across screen sizes. Verify all migrations twice and retain build cleanup after the verifier completes.

## Rationale and rejected alternatives

The single shared commitment ledger makes the competing claims on a branch's stock explicit and gives availability queries an RLS-safe non-PII source. The common lock protocol is essential because current stock writers and cross-branch create operate under different branch permissions. A separate ledger has migration and invariant cost; enforce source linkage and audit it against source states so it cannot drift. A direct sum over reservation and transfer tables is smaller but requires cross-branch RLS policies that can unintentionally expose customer information. A pickup-only lock or a standalone reserve API would be unsafe because ordinary checkout and stock adjustments currently ignore holds. Marking a hold collected in a standalone API before sale would re-open the stock race; only the sale transaction can collect it. Reusing a transfer for a pickup was already rejected by the project council because the customer can visit the stocking branch without moving stock.
