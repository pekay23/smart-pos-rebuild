# Customer credit sales and receivables

## Decision and accounting contract

Customer credit is a separate receivable, not a tender or a payment option. Checkout may leave part of an otherwise completed sale unpaid only when the cashier attaches an active customer and that customer has an enabled credit term in the branch currency. Captured tenders plus the on-account remainder must equal the sale total exactly. A sale without a customer, without terms, or beyond remaining credit is rejected before any stock, ticket, proof, sale, or journal write commits.

Credit terms are tenant-wide per customer and currency, so owner/admin/manager review sees one exposure across all branches using that currency. Different currencies have independent limits and balances. Credit-limit changes require the existing customer-management authority, an expected revision, a reason, and an append-only audit event. Cashiers can view available credit during checkout but cannot edit terms.

The credit exposure check and sale commit serialize against the current customer/currency term row in the same database transaction. The cashier runtime role must not receive term-update privileges merely to take this lock; the selected design puts cross-branch exposure and issuance behind a narrowly scoped database capability. The limit check uses outstanding invoice balances, not cached UI totals. Receivable amounts and limits use integer minor units; a configured limit of zero means credit is disabled.

## Records and lifecycle

- Each on-account sale creates one immutable receivable invoice linked to the sale, customer, tenant, branch, currency, cashier and due date in the same transaction as stock movements, tenders and journal posting.
- Collections are separate immutable records with source method, amount, currency, reference, actor, timestamp and idempotency key. Allocations cannot exceed the invoice's open balance. Exact retries replay the original collection; changed payloads conflict.
- Credit notes, cancellations and refunds create compensating records. They do not edit the original sale or receivable. Refund allocation must first settle or reverse outstanding receivable exposure; money collected is refunded only through the existing refund policy and provider status is not inferred from a typed reference.
- Overdue aging is a read model derived from due date and remaining balance. It never changes the ledger. Reports group by currency and clearly distinguish open, partially collected, overdue and written-off balances.

## Journal behavior

At sale completion, debit each actually captured tender clearing account and debit Accounts Receivable for the on-account remainder; credit revenue, tax payable and inventory/COGS using the existing immutable sale snapshots. The journal must balance before commit. A collection debits its recorded tender clearing account and credits Accounts Receivable. A cash collection from a station drawer also records one linked drawer inflow and requires the current lease and signed financial-operation proof. Manually recorded external terminal/bank/mobile-money collections remain explicitly unverified until an approved provider integration confirms settlement.

Credit-note and refund journals reverse only the source amounts supported by immutable records. If the original sale has partial coverage, the reversal preserves that limitation and reports the uncovered amount for review; it never invents historical costs or silently changes an old journal.

## Authorization and data boundaries

- Sale credit uses the existing cashier-only checkout authorization and signed station proof. A customer must be active, belong to the same tenant, and be visible to the authorized branch/station.
- Credit-term creation and revision require `customers:manage` at tenant scope and an active owner/admin/manager membership. Cashier requests cannot carry or override credit limits.
- Collection entry requires the appropriate cashier lease for drawer cash; manager/admin collection review and correction uses a separate permission and append-only correction records.
- Every new table uses forced row-level security, composite tenant/customer/sale/branch foreign keys, least-column runtime grants and tenant/branch scope derived from the authenticated API context.
- Receipts show the amount paid, amount placed on account, due date and remaining balance without disclosing credit limit or other branches' activity.

## Implementation sequence

1. Add migration for currency-specific customer terms, immutable receivable invoices, collection records and allocation records; add forced-RLS policies, supporting indexes, append-only triggers, role grants and migration assertions.
2. Extend signed checkout input with an explicit on-account amount and due-date policy. Lock terms, compute authoritative outstanding balance, create the invoice and post a balanced AR journal atomically with the sale. Preserve exact idempotent replay and fail closed for unsupported currencies/terms. **Partial:** signed hosted checkout accepts split or full on-account amounts, serializes against term edits, enforces current customer/currency exposure server-side, and atomically writes the immutable invoice, stock, sale and balanced AR journal. The restricted API integration verifies successful full-credit checkout, invoice term/due snapshots, AR debit, receipt API balance/due fields, and over-limit rejection without stock consumption. Partial tender display and due-date print layout remain open.
3. Add idempotent collection APIs, including signed drawer-linked cash collection and a separately labelled manual external collection path. Verify concurrent collection caps, exact retry, changed-payload conflict, drawer linkage and journal balance under restricted PostgreSQL roles. **Partial:** the signed cash API, atomic drawer/register event, balanced journal and audit are implemented; a cashier-only SQL capability lists compact open invoice balances across the tenant without granting raw cross-branch invoice access. The hosted register has a cashier form to allocate cash to selected open invoices, record an optional reference, submit idempotently and refresh credit/drawer state. Manual external collection, provider confirmation, direct route retries and concurrent collection acceptance remain open.
4. Add owner/admin/manager credit-term editing and customer exposure history; add cashier checkout disclosure and amount-due receipt line. Include clear blocked/remaining-credit errors before final sale confirmation. **Partial:** tenant-scoped term list/update/history and the hosted customer editor are implemented; hosted checkout now displays current available credit, accepts an on-account amount, rejects malformed/over-limit amounts and reports the credited amount. The signed API repeats the check. The current sale print layout and historical receipt rendering still need the on-account amount and exact due date displayed; authenticated cashier UI review remains open.
5. Add currency-specific aging, collections and exposure reports, CSV exports and append-only reviewed credit adjustment/settlement workflow.
6. Extend refund and return flows to handle sales with existing receivable balances, then run the full restricted tenant/operator regression and authenticated role-based browser review. **Partial:** to protect the ledger, the API and register currently block refund/void of sales with an on-account balance until immutable credit-note/receivable correction records are implemented.

Architecture synthesis: `sales::commit` remains the transaction owner. The implemented path calls the existing aggregate-only customer credit-position capability under a customer/currency advisory lock, then inserts the immutable invoice through the scoped cashier policy in the same transaction as sale, stock and journal writes. The term editor takes the same lock. Integration coverage now exercises the successful and rejected paths under the restricted runtime role. Keep invoice reads behind the existing worker capability; extract issuance into a typed receivables service only if it can preserve the current transaction boundary and narrow grants. Refunds remain blocked for credit sales until immutable credit-note and exposure-correction records exist.
