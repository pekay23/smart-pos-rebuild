# Cloud identity and PostgreSQL security review

**Reviewer:** independent senior security architecture review  
**Date:** 30 October 2026  
**Scope:** cloud identity/PostgreSQL choices for Advanced POS behind the planned independently deployable Rust API. This is a design review, not an implementation audit.

## Recommendation

Adopt **ZITADEL OIDC + PostgreSQL through the Rust API** as the preferred initial shape, with memberships, branch/station authorization, entitlements, and audit authority owned by the Rust service/database. Use Authorization Code + PKCE for browser/native clients, validate access-token signature, issuer, audience, expiry, authorized client, and intended token type against cached JWKS, and keep access tokens short-lived. Use introspection or a server-side session/revocation check for sensitive actions requiring immediate logout/revocation; a locally verified JWT alone remains valid until expiration. ZITADEL supports asymmetric JWT/JWKS verification, OIDC introspection/revocation endpoints, hosted or custom passkey ceremonies, and its organization model. [ZITADEL web keys](https://zitadel.com/docs/guides/integrate/login/oidc/webkeys), [OIDC endpoints](https://zitadel.com/docs/apis/openidoauth/endpoints), [passkeys](https://zitadel.com/docs/concepts/features/passkeys), [organizations](https://zitadel.com/docs/guides/manage/console/organizations)

This recommendation is conditional on a short proof of concept for the exact Rust OIDC/JWT stack, custom authentication domain and WebAuthn domain association, native system-browser PKCE, and organization/tenant claim mapping. Treat ZITADEL organizations as identity-provider organization boundaries only; the app's own `tenants`, membership scope, branch/station scope, roles, and entitlement state remain authoritative. Never authorize a resource solely because its tenant ID appears in a client-selected token claim.

The project’s own architecture decision calls for an API-first design, server authority for checkout/refunds/stock/audit/role scope/entitlements, and no direct client database access. Its implementation tracker says the present Rust API is only a stateless preview and has no cloud identity, tenant data, PostgreSQL, or persistence. Therefore provider choice must not blur the Rust API boundary or imply already-shipped cloud security. [Implementation tracker](../../../docs/IMPLEMENTATION_TRACKER.md), [Multi-client architecture ADR](../../clients/MULTI_CLIENT_ARCHITECTURE.md), [Commercial platform plan](../../../docs/PRODUCT_COMMERCIAL_PLATFORM_PLAN.md)

## Scorecard

Scores are 1 (weak/high burden) to 5 (strong/low burden) for this product and this Rust API architecture, not a general provider ranking. Weighted considerations: revocation + tenant authority, passkeys/native breadth, Rust/API fit, secret boundary, and operational risk.

| Deployable shape | Score | Assessment |
| --- | ---: | --- |
| **1. ZITADEL OIDC + PostgreSQL → Rust API** | **22/25** | Best fit. Standards-first OIDC, JWKS and introspection/revocation options; first-party passkeys and managed orgs; clean separation between identity and POS authorization. Main risk is operating/configuring a second domain model and ensuring exact native passkey association and claim freshness. |
| **2. Supabase Auth/Postgres + Rust API** | **20/25** | Strong alternative if the team wants integrated Postgres operations. Asymmetric JWT signing/JWKS fits Rust verification; built-in RLS and experimental passkeys. JWT revocation/cache semantics and current passkey experimental status are material concerns; if Rust connects with a privileged database role, RLS is only defense in depth and must not substitute for Rust authorization. |
| **3. Clerk + Neon/Rust API** | **18/25** | Polished identity and organization UX, short-lived JWTs and straightforward JWKS validation. Clerk organization claims encode active organization/role, but membership or role changes can lag token refresh; organization switching and timely membership revocation need explicit API-side checks. Neon is a database service, not an auth/RLS policy solution by itself. |
| **4. Self-hosted Better Auth service + Postgres/Rust API** | **15/25** | Maximum control and no third-party identity dependency, with documented passkey, organization and JWKS plugins. Highest operational and security ownership: secure deployment, email/recovery, abuse controls, signing-key storage/rotation, incident response, upgrades, monitoring and cross-service session revocation all become product responsibilities. More moving parts and a second service before the cloud API exists. |

## Security comparison

### 1. ZITADEL OIDC + PostgreSQL through Rust API

- **Token validation/revocation:** Asymmetric OIDC signing and JWKS verification give the Rust service local validation. ZITADEL exposes introspection to check revocation and a revocation endpoint; introspection adds a network dependency and latency but is the correct option for immediate session kill on high-risk operations. Cache JWKS with `kid` refresh-on-miss and a bounded stale-key policy. [OIDC web keys](https://zitadel.com/docs/guides/integrate/login/oidc/webkeys), [OIDC endpoints](https://zitadel.com/docs/apis/openidoauth/endpoints)
- **Memberships:** ZITADEL has organizations, but POS tenant membership is richer than a provider org: one business has branch/station-scoped staff and owner recovery. Keep a canonical app membership table and authorize each resource against it. Provider org claims can guide login/onboarding, not replace database authorization.
- **Passkeys:** First-party passkeys cover passwordless and MFA flows; ZITADEL warns passkeys bind to the domain, recommending a custom domain. Native iOS/Android clients need issuer-served association files. Reserve the long-lived identity domain before enrollment; test roaming credentials and shared-till personal identity constraints. [Passkeys](https://zitadel.com/docs/concepts/features/passkeys), [native app links and passkey guide](https://zitadel.com/docs/guides/integrate/login-ui/passkey)
- **Rust/API and secrets:** Standards-based HTTP/OIDC and public JWKS are a straightforward Rust fit. Keep confidential client credentials only in server secret storage; public native clients use PKCE and no embedded client secret. Rust API alone holds PostgreSQL credentials and all payment/provider secrets.
- **Risk:** Provider account/project misconfiguration, claim mapping, token freshness, tenant/provider-org mismatch, and uptime dependence. Mitigate with database memberships, short token lifetime, issuer/audience allowlists, audit logs, and tested provider outage behavior.

### 2. Supabase Auth/Postgres + Rust API

- **Token validation/revocation:** Supabase recommends asymmetric signing keys and publishes JWKS for local verification. Its docs explicitly warn external API verifiers may continue trusting a revoked key while JWKS caches remain warm (edge and library caches can persist); Supabase internal products have stronger instantaneous revocation. Do not assume a signed JWT is instantly revoked by the Rust API. Use brief access-token lifetimes and a denylist/session epoch or online check for immediate disablement. Avoid legacy HS256/shared JWT secret. [Signing keys](https://supabase.com/docs/guides/auth/signing-keys), [JWT verification](https://supabase.com/docs/guides/auth/jwts)
- **Memberships/RLS:** Supabase Auth integrates naturally with Postgres RLS and JWT claims. RLS is useful defense in depth, but this product has a centralized Rust workflow API. If that API uses a service/owner connection, it can bypass end-user RLS context; set transaction-local actor claims and use a least-privilege non-owner role if relying on policies. Keep application membership and authorization in Rust regardless. [RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)
- **Passkeys:** Native/web passkey support exists but is explicitly **experimental**, requires SDK opt-in and current client versions. Product plans require broad web, desktop, Android, iOS and later Harmony coverage; SDK/ceremony behavior and RP domain must be proven before committing. [Passkey guide](https://supabase.com/docs/guides/auth/passkeys)
- **Rust/API and secrets:** Asymmetric JWTs can be validated in Rust and the Postgres connection remains server-side. Supabase service-role/secret keys must never ship to clients. Decide explicitly whether Rust talks to Supabase Postgres directly or uses its APIs; direct privileged DB access bypasses the intended user-scoped RLS semantics unless deliberately reconstructed.
- **Risk:** Tight platform coupling, experimental passkey lifecycle, JWT revocation lag outside Supabase, and false confidence from RLS when a privileged Rust DB connection is used.

### 3. Clerk + Neon/Rust API

- **Token validation/revocation:** Clerk supports direct JWT verification via instance JWKS and documents session JWTs refreshed every 60 seconds, while server-side session state preserves a fast revocation path. This reduces—but does not eliminate—the window in which a copied JWT may be usable. Clerk recommends validating signature, expiry and authorized party (`azp`). [Manual verification](https://clerk.com/docs/guides/sessions/manual-jwt-verification), [session architecture](https://clerk.com/docs/guides/how-clerk-works/overview)
- **Memberships:** Clerk session tokens include the active organization ID, slug, role and permissions. The token represents an active org, not an exhaustive POS membership matrix. Custom claims can be up to about a minute stale. Ask Clerk/backend for fresh membership state on high-risk changes and persist POS scope/roles in the application database. Keep tenant switching explicit and server-authorized. [Session tokens](https://clerk.com/docs/guides/sessions/session-tokens), [custom session tokens](https://clerk.com/docs/guides/sessions/customize-session-tokens)
- **Passkeys:** This review did not verify first-party Clerk passkey support in current official sources; treat the POS passkey requirement as an integration gap until verified. Do not conflate Clerk/MFA support with WebAuthn passkeys.
- **Rust/API and secrets:** JWKS verification is simple for Rust. Store Clerk secret key and Neon connection string only in API secret storage. Neon is standard PostgreSQL; its separate Neon RLS/Data API facilities can bind JWT claims to policies, but if using only a Rust API and direct DB connections, policy context must be established safely per transaction. [Neon RLS overview](https://neon.com/blog/introducing-neon-authorize)
- **Risk:** Provider-specific active-organization claims can be misinterpreted as authorization; membership freshness and provider API dependency; Neon database credentials with superuser/BYPASSRLS capability can nullify policy assumptions. Use a least-privilege SQL role and keep Rust checks authoritative. [Neon role guidance](https://github.com/neondatabase/website/blob/main/content/docs/manage/roles.md)

### 4. Self-hosted Better Auth service + Postgres/Rust API

- **Token validation/revocation:** Better Auth’s JWT plugin provides `/token` and JWKS-verifiable JWTs for external services, separate from its primary session cookie. Its default JWT expiry is 15 minutes. Stateless Rust verification cannot observe session revocation until expiry unless the API also checks state or token/session version. [JWT plugin](https://better-auth.com/docs/plugins/jwt)
- **Memberships:** Organization plugin supports org/member management, but the POS service still needs its own branch/station membership model and checks. Avoid treating an active org claim as adequate tenant isolation. [Plugins](https://better-auth.com/docs/plugins)
- **Passkeys:** Official passkey plugin supports WebAuthn with configurable RP/origin and UV requirements. It is a credible functional option, but operational ownership of challenge/session lifecycle, domain, recovery policy and platform coverage remains with the product team. [Passkey plugin](https://better-auth.com/docs/plugins/passkey)
- **Rust/API and secrets:** JWT/JWKS fits Rust. Keep Better Auth signing material in the auth service only and separate its database/role from application API privileges where practical. Any auth service compromise can mint identities, so isolate network access and restrict DB access.
- **Risk:** The team becomes the identity provider operator: patch cadence, secure key management/rotation, recovery and email deliverability, rate limiting, DDoS protection, abuse detection, backups, HA, monitoring, audit and incident response. This is not a low-ops choice merely because the software is open source.

## Required design controls regardless of provider

1. Authentication proves the person; the Rust API derives `ActorContext` from a validated access token and loads current app memberships/role scopes. Never accept tenant, branch, station, owner or permission assertions from request JSON as authority.
2. Validate token `iss`, exact `aud`, `exp`, `nbf`, allowed signing algorithm, `kid`, token purpose/type and (where applicable) `azp`. Reject ID tokens at APIs. Refresh JWKS on unknown `kid`; pin trusted issuer URLs and bound cache staleness.
3. Use short-lived bearer access tokens. Native clients use system browser Authorization Code + PKCE and OS secure storage; browser clients should use a same-site HttpOnly session/BFF where feasible, with CSRF defenses. Do not put signing secrets or database credentials in desktop/mobile/web bundles.
4. Re-check current membership for each tenant-bound request. For especially sensitive actions, require recent reauthentication/passkey and immediate session revocation checks. Do not encode long-lived branch/station permissions into a token and assume they are current.
5. In Postgres, enable RLS for tenant-owned tables as defense in depth, force it where appropriate, and ensure app connections are neither table owners nor `BYPASSRLS` roles if policies are meant to execute. Still retain Rust authorization and transactional business invariants. Test cross-tenant reads/writes, background jobs, exports, sync, webhook paths, and connection-pool context leakage.
6. Separate operator identity/audience and sessions from tenant identity. Require strong MFA/passkeys for operators, explicit audited support grants, and no universal support credential.
7. Reserve the cloud RP/auth domain before passkey rollout. Verify exact origin/RP ID, UV, challenge single-use/expiry, account recovery, credential removal and tenant/user binding. Keep a second recovery method before allowing last-factor removal.
8. Establish incident procedures for account suspension, session revoke, issuer/JWKS outage, signing-key compromise/rotation, database credential rotation, and tenant-wide membership removal.

## Decision caveats

- This review scores choices against the documented API-first design. It does not prove any provider's SLA, pricing, regional processing location, contract terms, or certification status; those require separate procurement/legal review.
- ZITADEL organizations do not remove the need for application tenants and scoped memberships. Supabase RLS is not a substitute for Rust endpoint authorization. Neon RLS is an optional policy mechanism and may not apply when the service connects with a bypass-capable role.
- All provider-specific facts were checked against official documentation on 30 October 2026; provider documentation and SDK support can change before implementation.
