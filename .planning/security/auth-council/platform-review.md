# Auth platform council: platform and operations review

**Reviewed:** 2026-10-30  
**Scope:** Advanced POS with a Rust API and custom web, Windows, macOS, Linux, Android, iOS, and HarmonyOS clients; web deployment on Vercel; cost-conscious prototype that is not required to run in production for free.

## Recommendation

**Use ZITADEL Cloud as the initial identity provider (8.5/10).** It speaks standard OIDC/OAuth2, supports PKCE for native/public clients, has passkeys available, and keeps identity separate from the POS's application database and Rust API. Its current free tier has a low but usable ceiling (100 daily active users, one instance, 5,000 management API requests); crossing into production-scale traffic means a real monthly bill (Pro starts at $100/month). The major product fit is broad client support through OIDC, not a language-specific SDK. Verify the chosen Cloud region and service terms before storing customer data there.

Keep POS domain data in a separate PostgreSQL database. Have Rust validate access tokens against ZITADEL's issuer/JWKS and map the stable subject (`sub`) to an internal tenant/user record. Avoid putting business authorization rules solely in identity-provider roles/claims. That keeps the mobile and desktop clients interoperable and reduces migration coupling.

If the pilot needs deeply integrated Postgres auth/data and minimizes the number of vendors, **Supabase Auth + Postgres (7.8/10)** is the closest alternative. For this app, passkeys are explicitly experimental and the free database can pause after one week of low activity; use paid Pro for any live pilot depended on by users. **Clerk + Neon (7.4/10)** has polished client SDKs and production passkey features, but puts auth and database with two vendors and Clerk's production capabilities / MRU pricing should be checked against its chosen plan. **Better Auth + Postgres (7.1/10)** gives maximum data and hosting control with low recurring license cost, but makes this team the operator of account security, uptime, mail delivery, upgrades, incident response, and multi-client integration. It is a good option if self-hosting is a deliberate product capability, rather than a way to avoid an early bill.

Scores reflect this product's polyglot client coverage, Rust verification path, operational burden, prototype cost, ability to migrate, and maturity of passkeys. Weighted judgment, not vendor benchmark. A user's device can support passkeys independently of whether every OS integration or HarmonyOS browser does; preserve a fallback sign-in method until each target is validated.

## Per-option findings

### ZITADEL

- **Pricing/free limits:** Official pricing currently lists free at $0 with 100 daily active users, unlimited stored users/organizations, one instance, three active external identity providers, and 5,000 management API requests. Pro starts at $100/month with 25,000 DAU included and custom domain; the detailed table is the source for exact overage/feature terms. Free is useful for a prototype, not a production availability commitment. The pricing page describes a 99.5% uptime guarantee for Pro and 99.95% elsewhere in its summary; verify which SLA actually attaches to a purchased plan.
- **Passkeys and clients:** ZITADEL documents passkeys/FIDO2 and native-app association files. Native Android/iOS/desktop clients use Authorization Code + PKCE; Rust API can validate ordinary OIDC JWTs using public keys. Web can use OIDC too. HarmonyOS is not a first-party SDK claim here; use its browser/system OIDC support and prove redirects/deep links on target devices.
- **Deployment/operations:** Cloud is managed. Self-hosted deployment requires PostgreSQL 14–18, container runtime, HTTP/2-capable reverse proxy, backups, secrets/key rotation, monitoring, upgrades, and recovery. That is a substantial operations responsibility for an auth control plane. Cloud also allows a self-hosted/custom login UI, including documented Vercel deployment.
- **Regions/data:** Cloud pricing currently lists EU, US, Switzerland, and Australia residency. Confirm desired region availability, backups, and contract scope before selecting; this review did not establish a Ghana/Africa region.
- **Lock-in:** Low-to-moderate. OIDC standard flows and JWTs minimize client coupling; ZITADEL-specific admin APIs, actions, management model, claim mapping, and hosted UI add migration work. Keep internal IDs and authorization in POS DB.
- **Official sources:** [Pricing](https://zitadel.com/pricing), [detailed pricing](https://zitadel.com/pricing/detail), [native and application types](https://zitadel.com/docs/guides/manage/console/applications-overview), [passkeys](https://zitadel.com/docs/concepts/features/passkeys), [self-hosting requirements](https://zitadel.com/docs/self-hosting/manage/requirements), [self-hosting overview](https://zitadel.com/docs/self-hosting).

### Supabase Auth + Postgres

- **Pricing/free limits:** Current pricing lists Free at 50,000 MAU, 500 MB database, 5 GB egress, 1 GB storage, two active free projects, and project pausing after a week of inactivity. Pro starts at $25/month, includes 100,000 MAU and $10 compute credits; additional compute/projects can add cost. The platform docs explicitly say paid projects do not pause for inactivity. Free lacks backups, branching, advanced security features, and an availability SLA suitable for a relied-on production POS.
- **Passkeys and clients:** Current official guide labels Auth passkeys **Experimental**, warns the API may change, and lists supported JS, Flutter, and Swift client versions plus native passkey plugins/platform calls. Native Android is represented by Android app origin support; confirm complete Android/HarmonyOS client path against the chosen client stack. Rust is not the primary Supabase Auth SDK path; Rust API can validate Supabase-issued JWTs using the project JWKS, but check signing-key configuration and refresh/session design.
- **Deployment/operations:** Managed Supabase is quickest. Self-hosting is documented, but the whole platform is several services rather than just Postgres/Auth; budget ops effort for updates, storage, edge functions, backups and observability. Vercel can host the custom web app while Supabase hosts DB/Auth.
- **Regions/data:** Project region is chosen at creation; free has no database branching. Branching is a paid feature. Projects are separate Supabase instances, so dev/prod separation adds project/compute cost on paid plans.
- **Lock-in:** Moderate-to-high if POS uses Supabase-specific Auth, RLS, Realtime, Storage, or generated APIs throughout. Lower if the Rust service owns data access and Supabase is used only for OIDC-like identity/JWT verification. PostgreSQL and exportability help, but hosted Auth schema/provider semantics are Supabase-specific.
- **Official sources:** [Pricing](https://supabase.com/pricing), [project pausing](https://supabase.com/docs/guides/platform/free-project-pausing), [passkey guide](https://supabase.com/docs/guides/auth/passkeys), [database regions](https://supabase.com/docs/guides/platform/regions), [branching](https://supabase.com/docs/guides/deployment/branching), [self-hosting](https://supabase.com/docs/guides/self-hosting).

### Clerk + Neon

- **Pricing/free limits:** Current Clerk pricing lists a free limit of 50,000 monthly retained users (MRU) per app; MRU is not identical to MAU. Its pricing page distinguishes development and production instances and gates items such as MFA, custom session policy, and enterprise connections by plan. Treat the free plan as prototype/development budget, and price the actual set of production-required features before selecting. Neon has its own free allowance and paid consumption pricing; don't assume the combined stack remains free or single-vendor-simple.
- **Passkeys and clients:** Clerk has passkeys in web/native docs and recently documented passkeys as an MFA second factor. The new native second-factor path requires minimum iOS/Android/Expo SDK versions; web also has minimum package versions and per-instance opt-ins. Native app auth via hosted browser or SDK is documented for Android/iOS/Expo. Linux desktop and HarmonyOS would use standards/custom flows rather than assume a supported native Clerk SDK. A Rust API can verify Clerk JWTs, but ensure token templates/audience/issuer/JWKS are configured consistently.
- **Deployment/operations:** Clerk is managed auth; Neon is managed serverless Postgres. Vercel integration is natural for web. Neon compute scales to zero on lower tiers, which saves prototype cost but creates cold-start latency; production endpoints can be configured for always-on behavior at usage cost. Operations are low, but billing/incident/support are split between two providers.
- **Regions/branching:** Neon provides copy-on-write database branches and selectable regions; branches are excellent for schema preview/testing. Verify current plan quotas and region list for the desired geography. Auth users remain in Clerk, while POS data is in Neon, requiring distinct export/restore and region considerations.
- **Lock-in:** Moderate. Neon is PostgreSQL with branches and standard connection semantics, relatively portable. Clerk's session/user model, components/hooks, webhooks, and organization/permission APIs are vendor-specific; use JWT/OIDC boundaries in Rust and internal user IDs for business data to keep migration reasonable.
- **Official sources:** [Clerk pricing](https://clerk.com/pricing), [Clerk passkeys](https://clerk.com/docs/guides/secure/passkeys), [passkey MFA announcement](https://clerk.com/changelog/2026-10-29-passkey-second-factor), [native hosted auth](https://clerk.com/docs/android/guides/account-portal/hosted-auth), [Neon pricing](https://neon.tech/pricing), [Neon branching](https://neon.tech/docs/introduction/branching), [Neon regions](https://neon.tech/docs/introduction/regions).

### Better Auth + Postgres

- **Pricing/free limits:** Better Auth is a self-hosted open-source library rather than a hosted auth service with a free/pro MAU quota. Its runtime runs in the application server and persists to a supported database. Compute, database, email/SMS delivery, domain, monitoring, backups, security operations, and support remain real costs. Vercel functions plus Neon/Postgres can lower initial spend, but avoid relying on a sleep-prone or ephemeral runtime for production sessions.
- **Passkeys and clients:** Official passkey plugin supports WebAuthn through SimpleWebAuthn; it documents web and Expo integration. Better Auth also offers an OAuth 2.1/OIDC provider plugin, but operating the provider and client flows is the app team's responsibility. Check Android/iOS/HarmonyOS/desktop implementations separately; clients must use appropriate native credential APIs or browser-based system auth. A Rust API cannot call Better Auth's server library directly; it can consume OIDC JWTs if the OAuth provider plugin is used and configured to issue verifiable tokens, or the app must create another secure token-verification boundary.
- **Deployment/operations:** A JS/TS server is required for Better Auth, even though the business API is Rust. Deploy it as a separate service on Vercel or another Node host; share Postgres only with carefully designed schema, credentials, migrations, and availability controls. The operator owns secure cookies, rate limiting, abuse protections, session invalidation, mail delivery, database backups, upgrades and incident response. This operational burden is often hidden when comparing only license price.
- **Regions/branching:** Depends entirely on the selected Postgres host. On Neon, branches and regions come from Neon, not Better Auth. A self-hosted PostgreSQL operator chooses region and backups, but must build their own branching/preview workflow.
- **Lock-in:** Low-to-moderate at infrastructure/data level (open source, SQL tables and configurable adapters), but app-level session/cookie APIs and plugin schemas are Better Auth-specific. OIDC boundary can help clients switch; migration remains an engineering project and requires account/credential portability planning.
- **Official sources:** [Better Auth installation and databases](https://better-auth.com/docs/installation), [PostgreSQL adapter](https://better-auth.com/docs/adapters/postgresql), [passkey plugin](https://better-auth.com/docs/plugins/passkey), [OAuth/OIDC](https://better-auth.com/docs/plugins/oauth-provider), [Neon pricing](https://neon.tech/pricing).

## Rust API and cross-platform operating notes

All four can be made to work with a Rust API, but the cleanest shared pattern is a standards-based boundary: native/public clients use Authorization Code with PKCE; the Rust service accepts access tokens, checks signature, issuer, audience, expiry and required claims, then resolves `sub` to local POS identity. Do not accept an ID token as an API bearer token merely because it is a JWT. Do not place a provider's secret key in any desktop/mobile binary. Use short-lived access tokens and a deliberate refresh/session-revocation strategy suitable for offline POS operation.

For Vercel web, hosted authentication can use secure web redirects and cookies. Native clients need registered app links/custom URI schemes and PKCE. Windows/macOS/Linux do not share one universal passkey API; their browser and OS combinations need separate acceptance checks. HarmonyOS availability of Google Play Services and authenticator APIs varies, so retain a tested fallback and do not treat an Android SDK compatibility claim as HarmonyOS certification.

## Cost and production decision

For a short prototype, ZITADEL Cloud Free or Supabase Free is workable if the team accepts their limits and data is disposable. Since the requirement explicitly does **not** demand production for free, cost should not outweigh predictable operation: use paid tiers as soon as a live store depends on sign-in or data availability. Supabase Free's inactivity pause is a direct mismatch for a pilot left idle for a week. Better Auth avoids an auth subscription, but it does not make dependable production hosting free. ZITADEL's free DAU limit is small, yet provides a clean migration path via OIDC and the smallest long-term cross-client coupling among the managed options.

Before locking the choice, prototype one full flow in the Rust API and one native app: login with PKCE, access-token verification, logout/revoke behavior, tenant mapping, and passkey with fallback. This is a compatibility spike, not a reason to postpone the platform decision.
